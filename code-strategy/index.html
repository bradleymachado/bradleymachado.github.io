Code Strategy

2026

Most agent failures are context failures. The skill treats what each agent is allowed to read as a design decision, and puts a reviewer between every return and the work that depends on it.

Type
Claude Code skill and agent bundle: SKILL.md, nine subagent definitions (four executors, intake, review, three review gates), templates, a state file, a Stop hook
Role
Author. Designed and written for my own studio work; run on it since September 2026
Tools
Claude Code · Claude Fable, Opus, Sonnet · Markdown ledger · Python · MCP into Rhino, Grasshopper, Blender, MATLAB
Scope
Source intake, strategy plan, roster chart, tiered execution, review gates, progress log, closeout
Status
v1 in use on ARCH 575. v2.0 (context packets, review gates, roster chart) released 15 October 2026; download below
01 / Problem
Why

A studio project is a few hundred decisions over four months, made in tools that do not talk to each other: Rhino, Grasshopper, Ladybug, MATLAB, Revit, a slide deck. Running that through one long chat fails in a predictable way. The session fills with everything it has read, the plan drifts, and the model starts acting on the wrong half of its context. The only reviewer is me, at the end, after the error is already built into three downstream files. Code Strategy is the fix I built for that, and it runs the work I do every week.

02 / Context engineering
Packets and the ledger

Context is a budget. The default spends it on everything in the folder; the skill does the opposite. The orchestrator holds the plan and the tail of the log. Each subtask agent receives a packet cut from one shared ledger: its own section of the plan, the fixed-inputs table, the tooling rules, the measured values from the subtasks it depends on, and the acceptance checks it will be scored against. It does not receive the other sections, the other tasks' logs, or the source PDFs. Those were converted to Markdown twins at intake, and only the twin is read. What the packet leaves out, the agent cannot act on.

03 / Prompt engineering
One template, filled by the orchestrator

Every executor prompt is one template with the blanks filled in. It names one subtask, states the time budget, lists the output files with folder paths, and gives each acceptance check a numeric value computed at planning time, before any agent has a reason to want a particular answer. Two lines do most of the work. "Take the conservative default for anything the plan leaves open, record it with its revert cost, never ask a question" keeps the run moving. "Return exactly the REPORT block; nothing may follow" makes every return machine-checkable: PASS or FAIL per check, values with units, files, decisions. Any other shape is a FAIL.

04 / Agentic workflow
Orchestrator, tiers, ladder

One Claude Code session in the project folder is the orchestrator. It does none of the work: it spawns a fresh agent per subtask and verifies what comes back. Agents are tiered by model and effort. Opus at medium effort builds from a spec. Opus at high effort handles design moves and anything driving Rhino or Grasshopper over MCP. Fable handles optimization and corrections of Opus failures. Sonnet needs a justification in the plan. Three subtasks run in parallel once their dependencies pass. A failure retries one tier up; a second is a plan fault and the plan is revised; a third stops the run and asks me one question.

Hard stops

The run ends early for four reasons only: an action only I can take, such as opening an application or supplying a file; a brief with two readings that produce different deliverables and no conservative reading that satisfies both; a destructive step, anything that overwrites a file the run did not create or sends anything outside the project folder; a missing tool after one remediation attempt. Everything else is a logged default with a stated revert cost.

05 / Review gates
The third question

v1 verified two things after every subtask: the logged files exist, and every check is stated PASS or FAIL with a value. That catches a missing deliverable. It does not catch a correct deliverable the next task cannot use. v2 adds a reviewer one tier above the producer: a separate agent that receives the packet, the return, and the parent's section of the plan, and answers a third question. Does this result fit what the level above needs, in the names, units and format it expects. A return that fails the fit question goes back to the producer. It does not pass upward to break something later.

Why it matters, from the log

The case that forced this was a surrogate model. The subtask that trained neural networks on a 2,000-run facade sample passed its own checks: test R² above 0.99 on photovoltaic yield, solar gain on glass and the shade plate. The view objective it carried upward was 12 points high on average, 18 at worst. The error surfaced only because the next subtask re-simulated all 136 Pareto designs in Ladybug and the optimum was re-picked on simulated values. Under v1 that catch depended on the plan happening to include a re-simulation step. Under v2 the gate asks the fit question before the number moves.

06 / The roster chart
First product

Before anything runs, the skill now delivers two things together: the plan and a roster chart. Every master task, task and subtask is a card: what it does, which agent and tier runs it, which reviewer gates it, who it reports to, its status. Failed first runs stay on the chart beside their retry. When a subtask and its reviewer both miss the same thing, the chart points at one packet and one reviewer brief, and the question becomes concrete: more context, better prompting, or a higher tier.

07 / What it has run
Evidence

The Hybrid Hi-Rise page on this site was produced by a v1 run: a file index of nine text sources, a plan with check values, page copy checked against those sources for numbers, dates and banned strings, an image manifest, a QA pass. The facade cover study ran as a chain of subtasks: geometry library, 2,000-run sample, MATLAB surrogates, re-simulation, renders, a 15-slide deck, each returning a REPORT block and each logged. The progress log for the tower project is the record a reviewer can read without me in the room.

Stakes

The constraint that matters is not model capability. It is what each agent is permitted to know, and who checks the result before the next agent builds on it. Get that wrong and a better model fails faster, with more confidence and in more files. Get it right and the human's job moves from catching errors to deciding what the project is for.

08 / Download
Bundle

code-strategy_v2.0_portable.zip (34 KB, SHA-256 a7379c1c…0a24b). One skill, nine subagent definitions, five templates, a roster renderer, a permission template and a Stop hook. Portable edition: no personal paths, names or format rules. MIT.

Install

Copy .claude/skills/code-strategy/ to ~/.claude/skills/ and .claude/agents/*.md to ~/.claude/agents/. In a project folder, copy .claude/settings.json, .claude/hooks/ and .code-strategy/, fill the kickoff template, append CLAUDE_snippet.md to CLAUDE.md. Claude Code 2.1 or later.

Run

/code-strategy <brief path>. The session asks every open question one per turn, writes the plan and the roster chart, stops once for approval, then runs to closeout.
